# 構成（決定事項）

Windows 11 の PC で鳴っている音を、Android 端末で聴くための構成。ここに書いたことが決定事項の正本で、実装はこれに従う。変えるときは先にこの資料を直す。

## 1. 要件（利用者との確認で決まったこと）

| 項目 | 決定 |
|---|---|
| 用途と遅延 | 音楽を聴くだけ。**遅延は1秒程度まで許す** |
| 取る範囲 | **PC 全体の音**（既定の出力機器に出ている音） |
| PC のスピーカー | 転送中に PC 側を無音にする必要はない（どちらでもよい） |
| つなぎ方 | **Wi-Fi だけ**。受け手の Android は **1台** |
| Android アプリ | 入れてよい。**画面を消したまま聴き続けられること** |
| 配布 | **自分用**（ストアには出さない。コード署名もしない） |
| PC アプリの起動 | **手動で起動**（サインイン時の自動起動はしない） |
| 操作する側 | **Android で再生を押すと、PC が自動で送り始める** |
| Android の版 | 手元の端末は Android 16。**最低は Android 8.0（API 26）** |

## 2. 採った構成：HTTP で流し続ける方式（ネットラジオと同じ形）

```
┌──────────── Win11 PC（C# / .NET 10） ───────────┐        ┌────────── Android（Kotlin） ──────────┐
│ WasapiLoopbackCapture（既定の出力機器）         │        │ Compose の画面（接続先・再生/停止）     │
│   ↓ 音が届かない時間を無音で埋める              │        │   ↓                                      │
│ 48kHz ステレオに整える                          │  Wi-Fi │ MediaSessionService（前景サービス）      │
│   ↓                                             │  HTTP  │   └ ExoPlayer（バッファは 0.5〜1秒）     │
│ 圧縮（Ogg/Opus。駄目なら MP3）                  │ ─────→ │      ・通知／ロック画面の操作             │
│   ↓                                             │        │      ・Wi-Fi ロック・オーディオフォーカス│
│ HTTP サーバ（Kestrel）/stream を流し続ける      │        │      ・切れたら自動で再接続               │
│ タスクトレイに常駐（IP:ポート・ペアリングの数字）│        └──────────────────────────────────────────┘
└─────────────────────────────────────────────────┘
```

### 2.1 PC 側

- **形**: C# / .NET 10（長期サポート版）のタスクトレイ常駐アプリ。手動で起動する。当初は .NET 8 としたが、.NET 8 のサポートが 2026年11月10日に終わるため、利用者の了承を得て .NET 10 に変えた。
- **キャプチャ**: NAudio の `WasapiLoopbackCapture` で既定の出力機器の音を取る。既定の出力機器が変わったら取り直す。
- **無音で埋める**: ループバックは、何も鳴っていない間はデータを返さないことがある（どこかのアプリが音の出口を開いたままだと、無音のデータを返し続ける。試作で両方を見た）。そこで 20ms ごとに時計で刻んでバッファから1フレームを取り出し、足りない分を無音で埋めて、ストリームを途切れさせない（`FramePacer`）。時間は `TimeProvider` の単調な時刻（`GetTimestamp`。中身は `Stopwatch` と同じ）で計る。
- **圧縮**: 第一候補は **Ogg/Opus**（Concentus。C# だけで書かれていてネイティブの DLL が要らない）。128kbps、1パケット 20ms。ExoPlayer が終わりの無い Ogg/Opus のストリームを再生できるかを最初の試作で確かめ、駄目なら **MP3**（NAudio.Lame）に替える。
- **Ogg は自前で書く**: 既成の Ogg 書き出しはページが満杯になるまで溜めるため、数秒遅れる。5パケット（100ms）ごとに1ページを書いてすぐ流す。
- **配信**: ASP.NET Core の最小 API（Kestrel）で `GET /stream` を流し続ける。
- **送り始めと止め方**: `/stream` に接続が来たらキャプチャを始め、切れたら止める。PC 側のトレイには、送り始めるボタンを置かない（Android の再生がそのまま送り始めの合図になる）。
- **接続は1本（先勝ち）**: 受け手は1台なので、同時の接続は1本に限る。流している間に2本目の接続が来たら、**後から来た方を断る**（`409 Conflict`）。
- **切れた接続の見切り**: Wi-Fi の瞬断では、PC から見て古い接続が切れたと分からないまま残ることがある。そのままだと先勝ちのせいで、Android が繋ぎ直しても断られ続ける。これを防ぐため、送ったデータが一定の時間はけない（相手が受け取らない）接続は、切れたと見なして閉じる。見切るまでの時間は、試作では **1回の書き込みが5秒で終わらなければ** とした（`AudioStreamService.WriteTimeout`）。実機の瞬断で確かめて見直す。
- **待ち受け**: 同じ Wi-Fi の端末から繋げるよう、すべてのネットワークの口（`0.0.0.0`）の **ポート 48100** で待ち受ける（起動の引数 `--port` で変えられる）。Windows のネットワークの種類が「パブリック」だとファイアウォールに止められやすいので、手順書に「プライベート」にすることを書く。

### 2.2 Android 側

- **形**: Kotlin / Jetpack Compose / Media3（ExoPlayer）。最低 API 26（minSdk）、対象は手元の Android 16（targetSdk 36）。compileSdk は入っている SDK に合わせて 37。
- **画面を消したまま聴く**: Media3 の `MediaSessionService` を前景サービス（`foregroundServiceType="mediaPlayback"`）として動かす。Android 14 以降で要る `FOREGROUND_SERVICE_MEDIA_PLAYBACK` の権限も宣言する。通知とロック画面からの操作・オーディオフォーカス・Wi-Fi ロック（`setWakeMode(C.WAKE_MODE_NETWORK)`）を Media3 に任せる。メディアセッションの通知は、Android 13 以降の通知の許可（`POST_NOTIFICATIONS`）が無くても出せる。
- **暗号化しない HTTP の許可**: Android 9 以降は暗号化しない HTTP を既定で止めるので、`network_security_config` で許す（PC の IP は変わりうるので、名前を絞らずに許す。自分用として受け入れる）。
- **バッファ**: ExoPlayer の既定は数十秒ためるので、`DefaultLoadControl` を縮める。試作では、ためる量を 0.5〜1.5秒、再生を始めるまで 0.3秒、途切れたあと再開するまで 0.5秒とした。実機で途切れ方を見て見直す。
- **接続先**: 「PC の IP:ポート」を手で入れて保存する（自分用なので、mDNS による自動の発見は後回しにする）。初回は続けてペアリング（2.3）に進む。
- **切れたとき**: Wi-Fi の瞬断や PC の再起動で切れたら、間をあけて繋ぎ直す。試作では、**1秒から倍々に延ばし、15秒で頭打ち**にして、利用者が停止を押すまで回数の上限なく続ける（`ReconnectPolicy`）。繋がったら1秒に戻す。
- **ExoPlayer の中の再試行は切る**: ExoPlayer は読み込みが途切れると、HTTP の Range で「続きから」読み直そうとする。PC の配信はライブで続きが無く、新しいストリームが先頭（見出し）から届くので、続きから読むと Ogg の途中に別のストリームが混ざる。そこで再試行を切ってエラーをすぐ表に出し、上の繋ぎ直しで**最初から開き直す**（試作で、再試行を切らないと別の経路で静かに繋ぎ直してしまうことを見た）。

### 2.3 ペアリング（数字を選ぶ方式）と接続の鍵

同じ Wi-Fi にいる他の機器から聴かれないように、**最初の1回だけ**ペアリングし、以後は PC が発行した接続の鍵で繋ぐ。

#### 流れ

```
Android                                   PC（トレイ）
  │ ① 接続先（IP:ポート）を入れて「つなぐ」   │
  │ ──── POST /pair/start ────────────────→ │ ② 2桁の数字（00〜99）を作り、画面に出す
  │ ←─── 候補5つ（正解1つ＋外れ4つ、順不同） ─ │
  │ ③ PC に出ている数字と同じものを選ぶ       │
  │ ──── POST /pair/answer ────────────────→ │ ④ 合っていれば接続の鍵を発行する
  │ ←─── 接続の鍵 ─────────────────────────  │
  │ ⑤ 鍵を端末に保存                          │
  │ ──── GET /stream（鍵つき）─────────────→ │ ⑥ 鍵を確かめて送り始める
```

- 候補の5つは PC が作る。5つは互いに重ならず、正解は必ずちょうど1つ入る。
- 数字と候補は暗号用の乱数（`RandomNumberGenerator`）で作る。乱数は差し替えられる口から受け取り、テストでは決まった値を入れる。
- 接続の鍵は長い乱数（32バイト）とする。2桁の数字は、鍵を渡す相手を確かめるためだけに使う。
- 受け付けない間に `/pair/start` が来たら断り、Android は「PC で受け付けない状態を解いてください」と出す。
- 数字を出してから **2分** のうちに答えが来なければ、その数字を無効にする。Android はペアリングを最初からやり直す。期限切れは**外れた回数に数えない**。

#### 外れたとき

| 状況 | 扱い |
|---|---|
| 1回外れた | その数字を捨てて、新しい数字と新しい候補で作り直す |
| **続けて2回**外れた | **24時間、ペアリングを受け付けない** |
| 正解した | 外れた回数を0に戻す |

- 受け付けない状態は **PC アプリを起動し直しても続く**（期限と外れた回数を PC に保存する）。
- PC のトレイに **「受け付けない状態を解く」** を置き、持ち主が選び間違えたときは手で解ける。
- 受け付けないのはペアリングだけ。ペアリング済みの端末は、その間も鍵で繋いで聴ける。

#### ペアリング済みのとき

- 受け手は1台なので、ペアリング済みの間は**別の端末からの新しいペアリングを受け付けない**。端末を替えるときは、先にトレイで「ペアリングを解除」する。
- **「ペアリングを解除」**（トレイ）: 保存した鍵を消し、古い鍵を無効にする。端末を替えたときや手放したときに使う。

#### 答えを待っている間・鍵が無効になったとき（利用者と決めた）

- ある端末がペアリングを始めて答えを待っている間（最大2分）に、別の端末がペアリングを始めたら、**後から来た方を断る**。PC に出ている数字が途中で入れ替わらないようにする（接続の先勝ちとそろえる）。
- PC で「ペアリングを解除」したあと、古い鍵を持った Android が繋いできたら、Android は**鍵を捨ててペアリングの画面に戻る**（繋ぎ直しはしない）。
- Android で接続先（PC の IP）を変えても、**鍵は残す**（PC の IP が変わっただけのときに、ペアリングし直さずに済むように）。別の PC に向けた場合は、その PC が鍵を認めないので、上の「鍵が無効」の扱いになる。

#### 通信の取り決め

| 要求 | 応答 |
|---|---|
| `POST /pair/start` | 200: `{"pairingId", "candidates": [5つ]}`。409: ペアリング済み（`"reason": "paired"`）か、別の端末が答えを待っている（`"reason": "busy"`）。423: 受け付けない状態（`"lockedUntil"`） |
| `POST /pair/answer`（`{"pairingId", "answer"}`） | 200: `{"key"}`。400: 外れ（`"candidates"` に新しい5つ。PC には新しい数字が出る）。423: 続けて2回外れて、受け付けない状態になった。410: 数字の期限（2分）が切れたか、知らない `pairingId` |
| `GET /stream`（`Authorization: Bearer <鍵>`） | 200: 流す。401: 鍵が無いか、認めない鍵。409: 流している最中 |

- 鍵は **HTTP のヘッダ**（`Authorization`）で渡す。URL に入れると、ログやブラウザの履歴に残りやすいため。
- 鍵は 32 バイトの乱数を Base64URL にした文字列。PC は SHA-256 のハッシュだけを持ち、届いた鍵のハッシュと、時間の差が出ない比べ方（`CryptographicOperations.FixedTimeEquals`）で比べる。
- PC は、数字を出している間、**画面の右下（タスクバーを除いた作業領域の右下）に、白基調の小さなポップアップ**で数字を出す（利用者と決めた）。
  - 置き場所は、出す前と、出したあとにもう一度決める。置いた位置（狙った位置・実際の位置・画面の並び）はログに残す（2026-10-21、画面が3枚ある PC で、ほかの画面の真ん中に出たことがあったため。原因は突き止められていない）。
  - 出すもの: 2桁の数字、「端末で同じ数字を選んでください」の一言、残り時間（2:00 から 1 秒ごとに減る。外れて数字を作り直したら、また 2:00 から）、閉じるボタン（×）。
  - × で閉じても、ペアリングは続く（次に数字が変わったら、また出す）。
  - 出すときに入力の焦点を奪わず、タスクバーや Alt+Tab にも出さない（作業中の邪魔にならないように）。
  - 答えが合ったとき・期限が切れたときに消し、外れて作り直したときは数字と残り時間を替える。

#### 保存

- PC 側: 鍵そのものではなく**鍵のハッシュ（SHA-256）**と、受け付けない状態（期限・外れた回数）を、ユーザーごとの場所（`%LOCALAPPDATA%\AudioSwitcher\`）に保存する。PC は届いた鍵のハッシュを比べるだけなので、鍵そのものを持つ必要が無い。保存したファイルが読まれても、鍵は分からない。PC アプリを起動し直しても、鍵で繋がる。
- Android 側: 鍵を Android Keystore の AES 鍵（端末の外に出せない）で暗号化して保存する。
- 鍵と2桁の数字は、ログ・コミット・書き出しファイルに入れない。

#### 24時間の計り方

受け付けない状態は PC アプリを起動し直しても続けるので、単調な時計（`Stopwatch`）では計れない（起動し直すと 0 に戻るため）。期限は **UTC の時刻**で保存し、差し替えられる時刻の口（.NET の `TimeProvider`）から読む。全体ルールの「経過時間は壁時計の差で計らない」の例外で、理由は CLAUDE.md に書く。PC の時計を進めると早く解けるが、PC を触れる人は持ち主なので受け入れる。

#### 守りの強さ（既知の制約）

- 当てずっぽうでも1回で 1/5 の確率で当たる。続けて2回外れたら24時間止めるので、止まるまでに当てられる確率は約 36%（1 − 0.8 × 0.8）。何度も試すことはできない。
- 通信は暗号化しない HTTP なので、同じ Wi-Fi で通信を盗み見できる人には鍵が見える。自分用・家庭用として許す。気になる場合は、あとで HTTPS（自己署名の証明書を Android に覚えさせる形）にする。

### 2.5 文字起こし（利用者と決めた。2026-10-20）

PC から届いた音を、端末で日本語の文字に起こし、スマホの中の Obsidian の Vault に md ファイルとして保存する。

#### 決めたこと

| 項目 | 決定 |
|---|---|
| 動かす場所 | **Android 側**（音は端末の中ですでに復号されているので、ExoPlayer の途中から複製を取る） |
| 動かすとき | 再生の画面の切り替えで「入」にしたときだけ、再生している間に動かす |
| 文字起こしの方式 | **B: Groq の Whisper（無料枠）を主にする**。**A: Gemini API（AI Studio の無料枠）**と **C: Android の端末の中の音声認識**にも切り替えられる作りにする |
| 改行 | 句点（。）・「？」・「！」で改行する（「？」「！」は 2026-10-21 に利用者と決めて足した。半角の「?」「!」も同じに扱う）。「？！」のように続くときは、続いた記号のあとで 1 回だけ改行する |
| 空白 | **5秒以上**の無音を「（～秒空白）」（秒は整数）と書いて改行する。秒は端末の中で数える（文字起こしの方式には数えさせない） |
| 効果音・衝撃音・BGM | 区別できれば書かない |
| 保存先 | `/storage/emulated/0/Documents/SyncVault/30_Projects/Spaceまとめ/`。最初に1回だけフォルダを選んでもらい、その書き込みの許可を覚えておく（Storage Access Framework） |
| ファイル | 記録を始めた時刻を名前にする（例: `2026-10-20 2045.md`）。**1時間ごと**に区切り、続きは `2026-10-20 2045 (2).md` |
| 区切りを短くして確かめる（Debug 版だけ） | 1時間を待たずに区切りを確かめるため、Debug 版だけ、アプリの中の `files/debug_part_minutes` に分の数を書くと、区切りをその長さにする（利用者と決めた。2026-10-21）。書き方は `adb shell run-as io.github.tsarubucreate.audioswitcher.debug sh -c 'echo 3 > files/debug_part_minutes'`、戻すときはそのファイルを消す。Release 版では読まない。そのため、本番の1時間そのままでは確かめていないことになる |
| 長さ | 最大6時間程度 |
| 途切れ | PC との接続が切れるなどで**音そのものが届いていない**間は、5秒以上なら「（～秒途切れ）」と書いて改行する（声が無い「空白」と分ける） |
| プロパティ | md の先頭に Obsidian のプロパティを書く: `開始`（日時）、`何本目`（1, 2, …）、`方式`、`モデル`（短い名前）。本文はその下 |
| C の改行 | C は句点を付けないので、話の区切りの結果を1つにつき1行にする（句点は足さない）。B・A は返ってきた文を「。」の所で改行する |

#### B（Groq の Whisper）の使い方

| 項目 | 内容 |
|---|---|
| モデル | `whisper-large-v3-turbo`（文字起こしだけで足りる。翻訳は使わないので `whisper-large-v3` は考えない） |
| 送り先 | `https://api.groq.com/openai/v1/audio/transcriptions`。`language` に `ja` を付ける |
| 無料枠の上限（利用者が Groq の管理画面の Limits で確かめた。2026-10-20） | 1分あたり 20 回、1日あたり 2,000 回、1時間あたり音声 7,200 秒、1日あたり音声 28,800 秒 |
| 句点 | Whisper は日本語で句点を付けないことが多い（実機で、約 1 分が句点の無い 1 行になった）。句点の付いた例文（「こんにちは。今日はよろしくお願いします。では、始めましょう。」）を前置き（`prompt`）として送ると、その書き方に寄せて句点を付けて返す（実機で、すべての行が句点で終わるようになった）。「句点を付けて」という指示は効かない |
| 数え方 | 10 秒より短い音声も 10 秒として数えられる。そのため、声の区間をつなげて **10 秒以上**（上限 60 秒程度）にまとめて送る |
| 見通し | 6 時間（21,600 秒）は1日の上限に収まり、実時間で送るので1時間あたりの上限（実時間の 2 倍）にも収まる。区間を 10〜60 秒にすれば、回数も1分あたり・1日あたりの上限に収まる |

#### A（Gemini）の使い方（利用者と決めた。2026-10-21）

| 項目 | 内容 |
|---|---|
| モデル | 初めの値は `gemini-3.8-flash`。設定画面で名前を書き換えられる。Flash の無料枠が無くなったら、その時の最新の lite 系（例: `gemini-3.5-flash-lite`）に書き換える |
| 無料枠の確かめ（2026-10-21） | 公式の料金のページで、`gemini-3.8-flash`・`gemini-3.6-flash`・`gemini-3.5-flash-lite`・`gemini-3.1-flash-lite` はいずれも無料枠あり。無料枠を終える予定の記載は無い（2027-01-01 からの値段の変更は有料枠の話）。「10月9日に Flash の無料が終わった」という報道は、消費者向けの Gemini アプリの話で、API ではない |
| 送り方 | `generateContent` に、区間の音声を WAV（16kHz・モノラル）で `inline_data` として入れる。指示: 話し言葉だけを日本語で書き、効果音・衝撃音・BGM・歌は書かない、文の終わりに句点を付けて空白で区切らない、前置きや説明を書かない（句点のことは、実機で句点が付かず空白で区切った 1 行になったため足した。2026-10-21） |
| 考える量 | `generationConfig.thinkingConfig.thinkingLevel` に **`low`** を送る（利用者と決めた。2026-10-21）。公式の資料（2026-10-14 更新）で、gemini-3.8-flash の既定は `medium`、選べるいちばん少ない値は `low`（`minimal` はエラー）。`low` は無料枠のある 3.6 Flash・3.5 / 3.1 Flash-Lite でも使える。考えるのを切ることはできない |
| 返事を待つ時間 | **180 秒**（B は 60 秒）。実機で、24 秒の区間に約 1 分かかり、59 秒の区間は 60 秒の上限で 3 回とも打ち切られたため延ばした（利用者と決めた。2026-10-21）。「考える」量を減らす設定や、区間を短くする案は採らなかった |
| API キー | **ヘッダ（`x-goog-api-key`）で渡す**。公式の例は URL（`?key=`）に入れているが、URL は記録に残りやすいため使わない（全体ルール: 秘密を記録に入れない） |

#### B・A の区間の切り方と、失敗したとき（利用者と決めた。2026-10-21）

- 区間: 声が始まった所から溜め、**10 秒以上溜まって 0.8 秒以上の間（声の無い所）が来たら**送る。60 秒に達したら間が無くても送る。空白・途切れの印を書く前と、停止のときも、溜まっている分を送る（印より前の区間として順番を守る）。
- **区間の中の声が合わせて 0.5 秒に満たなければ、送らずに捨てる**（Claude の案。2026-10-21 の切り替えの確かめで、一時停止の「プツッ」という音だけの区間を送り、「（0秒文字起こし失敗…）」と書かれたため。Groq は 10 秒として数えるので無料枠の無駄になり、声の無い音からは文を作られやすい）。前に付ける 0.3 秒や、後ろの間は数えない。
- 失敗（通信の失敗、無料枠の上限、サーバの失敗など）: 間をあけて **2 回まで送り直す**。それでも駄目なら「（～秒文字起こし失敗：理由）」と書いて次へ進む（その区間の音は残らない）。API キーが認められないときは送り直さない。
- **無料枠の上限（429）のときは**、サーバが `Retry-After` ヘッダで示す秒数だけ待って送り直す。示されなければ 30 秒待つ（利用者と決めた。2026-10-21。Groq は 429 のときに `retry-after` を秒で返すと公式の資料にある。Gemini の資料には待ち時間を返す記載が無く、「間を広げながら送り直す」とだけある）。**示された待ち時間が 60 秒を超えたら、送り直さずに諦める**（Claude の案。1日の上限に当たると何時間も待てと返る見込みのため）。上限のほかの失敗（503 など）は 2 秒・4 秒あけて送り直す。
- **送る役はアプリで 1 本**にし、前の回の残りを送り終えてから次の回の区間を送る（利用者と決めた。2026-10-21。止めてすぐ再生し直したとき、前の回の送り直しと次の回が同時に送り、上限に当たったため）。止めたあとに届いた前の回の行は、区切りの時刻を過ぎていても、その回の最後のファイルに書く（印 1 行だけのファイルを作らないため）。
- **切り替えの順（優先度 B > A > C）**（利用者と決めた。2026-10-21）: 選んだ方式で**続けて 3 区間失敗したら**、優先度の順に次の方式へ切り替えて続ける。B を選んでいれば B → A → C、A を選んでいれば A → C。A の API キーが無ければ A を飛ばす。md に「（文字起こしを～に切り替えた：理由）」と書く。最後の方式でも失敗が続いたら、画面に知らせだけを出す。
- **下の方式に切り替えてから 10 分たつごとに、選んだ方式に戻して試す**（利用者と決めた。2026-10-21。6 時間の Space の初めに一時的に失敗しても、残りをずっと下の方式で書かないため）。md に「（文字起こしを～に戻した）」と書く。また 3 区間続けて失敗したら、もう一度下へ切り替える。10 分は単調な時計で計る。
- 方式の切り替え・API キー・モデルの名前は、再生の画面の「文字起こし」の欄の「方式を変える」から開く**別の画面**に置く（再生の画面は静かなまま）。API キーは Android Keystore で暗号化して保存する。

#### 無料枠の見張り（利用者と決めた。2026-10-21）

将来、B・A の無料枠が縮んだときに、画面から気づけるようにする。

- **前回の結果**: 1回の文字起こし（「再生」から「停止」まで）で、方式ごとに使った時間の割合、無料枠の上限（429）が返った回数（送り直しも1回と数える）、下の方式へ切り替えた回数を数え、止めたら文字起こしの欄に「前回 10/21 03:23 から 1時間2分: Groq Whisper 92%・端末の音声認識 8%、無料枠の上限 3回、切り替え 1回」と残す（次に止めるまで消さない）。止めたあとに届いた前の回の区間の結果は数えない。C の割合が高い・上限の回数が増えた、が続けば、枠が足りていない手がかりになる。
- **Groq の1日の回数の上限**: Groq は返事のたびに `x-ratelimit-limit-requests`（1日の回数の上限）を返す（公式の資料。音声の秒数の上限のヘッダは無い）。値を覚え、利用者が管理画面で確かめた 2,000 回より下がっていれば、文字起こしの欄に赤で「Groq の1日の回数の上限が下がっています（2,000 → ～ 回）」と出す。値が変わったときはログにも書く。
- **Gemini**: 公式の資料に上限を返すヘッダの記載が無いので、縮小そのものは検知しない。前回の結果の「無料枠の上限」の回数で傾向を見る。

#### 方式を選んだ理由

- **LLM を端末や PC に入れる案**は、性能が足りないため採らない（利用者の判断）。
- **Claude・Codex の API** は、サブスクが切れたときに止まるため採らない（利用者の判断）。
- **B（Groq の Whisper）を主にする**: 無料枠の公表値（1時間あたり音声 7,200 秒、1日 28,800 秒、1日 2,000 回）で6時間が収まる見通しで、送った音声を学習に使わないと明記している。指示には従わないので、句点での改行はこちらで行う。
- **A（Gemini API の無料枠）**: 日本語の質が高く、指示（効果音・BGM を書かない）にも従える。ただし無料枠では、送った音声と結果が Google の改善に使われ、人が読むことがある。回数の上限は公表されておらず、AI Studio で確かめる必要がある。
- **C（端末の中の音声認識）**: 費用もデータの心配も無いが、この端末で外から音を流し込めるか（`EXTRA_AUDIO_SOURCE`、Android 13 以降）、日本語を端末の中で扱えるか、句点が付くかが分からない。**作る前に端末で確かめる**（下の「C の確かめ」）。
- 入れ替えられる作りにするのは、どれか1つが使えなくなっても（無料枠の終了など）、設定を替えるだけで続けられるようにするため。
- Gemini の Live API（リアルタイムの音声の口）は使わない。音声だけでも1回のセッションが15分まで、接続は約10分で切れ、長く流すと文字起こしが届かなくなるという報告もあるため。30〜60 秒ほどの区間に分けて送る。

#### 作りの見取り図

```
ExoPlayer の復号した音（48kHz ステレオ）
  └─ 複製を取る（TeeAudioProcessor）→ 16kHz モノラルに変換
       └─ 無音の検出（端末の中）: 5秒以上の無音は「（～秒空白）」
            └─ 声のある区間を、無音の所で区切る（上限 60 秒）

```

- API キーは秘密なので、コードや記録に入れない。アプリの設定で入れてもらい、Android Keystore で暗号化して保存する。

#### C の確かめ

Debug 版にだけ入る確かめ用の画面で、実機について次を調べる。

1. 端末の中で動く音声認識があるか（`SpeechRecognizer.isOnDeviceRecognitionAvailable`）。
2. 日本語（ja-JP）が端末の中で使えるか、入っているか（`checkRecognitionSupport`）。
3. 外から音を流し込めるか（`EXTRA_AUDIO_SOURCE`）。PC の Windows の読み上げで作った日本語の音声を流し込む。
4. 句点が付くか、無音を挟んだときにどう区切られるか。

確かめ方: `app/src/debug` にだけ入る `AsrProbeActivity`（本番の版には入らない）。PC の Windows の読み上げ（Haruka）で作った 19.7 秒の日本語の音声（16kHz・16bit・モノラル。2つの話のあいだに 6 秒の無音）を、パイプで実時間の速さ（0.1 秒ずつ）で流し込んだ。

**結果（2026-10-20、Xiaomi の Android 16 / API 36）: C は使える。**

| 調べたこと | 結果 |
|---|---|
| 端末の中の音声認識 | ある（`isOnDeviceRecognitionAvailable` が true。中身は Google の Android System Intelligence） |
| 日本語 | **ja-JP が入っている**。ネットを使う言語は無し |
| 外から流し込む口 | 使えた。区切りながらの認識（`EXTRA_SEGMENTED_SESSION`）で、文ごとに `onSegmentResults` が届いた |
| 聞き取り | 5つの文をすべて正しく聞き取った（「こんにちは」「今日はスペースの文字起こしを試しています」「ここで少し休みます」「再開しました」「これが最後の文です」） |
| 句点 | **付かない**。そのかわり話の切れ目ごとに区切りの結果が届くので、区切りごとに改行する |
| 無音 | 6 秒の無音の前後で区切られ、そのあとも認識を続けた |
| 録音の許可 | **要らない**。マニフェストに書かず、与えてもいない状態で認識できた |

作るときの注意（確かめの途中で分かったこと）:

- パイプの読み口は、認識が終わるまで閉じない（`startListening` は依頼を後で送るので、すぐ閉じると「呼び出し側の失敗」になる）。
- 対応の言語を調べた認識器を、すぐ片付けて別の認識器を作ると、「サーバとの接続が切れた」になる（片付けの最中のため）。同じ認識器を使う。

まだ確かめていないこと: 数時間続けたとき、画面を消して前景サービスの中で動かしたときの振る舞い。

### 2.6 ふだん使う版（利用者と決めた。2026-10-21）

- **ふだんは、自分の鍵で署名した Release 版を使う**。Debug 版は、USB で繋いだ PC から `run-as` でアプリの中に入れる（アプリと同じ権限で、保存した API キーやペアリングの鍵を使えてしまうおそれがある）。確かめ用の画面（`AsrProbeActivity`）も Debug 版にだけ入り、ほかのアプリから開ける。
- Debug 版は別のアプリ（`io.github.tsarubucreate.audioswitcher.debug`、名前は「AudioSwitcher Debug」）にし、Release 版と並べて入れられるようにする。
- 署名の鍵と合言葉は利用者が作って持ち、git に入れない（作り方は docs/開発環境.md）。
- Release 版に替えるときは、入っている Debug 版とは別のアプリになるので、ペアリング・API キー・保存先のフォルダを入れ直す。
- 使わないときは、端末の USB デバッグを切る（利用者の運用）。

### 2.7 端末の音の文字起こし（利用者と決めた。2026-10-23）

PC の音を流すのと同じように、**端末の中で鳴っている X の Space の音**を取り込んで文字に起こす経路を足す。

#### 決めたこと

| 項目 | 決めたこと |
|---|---|
| 拾う音 | **X のアプリ（`com.twitter.android`）の音だけ**（アプリの番号 uid で絞る）。通知音やほかのアプリの音は拾わない |
| 仕組み | Android の再生中の音の取り込み（AudioPlaybackCapture、Android 10 以降）。始めるたびに、Android の画面のキャプチャの確かめ（MediaProjection）が出る（アプリから省けない） |
| 画面 | 再生の画面の上に「**PC の音 / 端末の音**」の切り替えを置き、いつもの「再生」「停止」で始める・止める。経過時間・文字起こしの欄・前回の結果は、PC の音と同じものを使う。同時には使わない（再生中は切り替えられない） |
| 文字起こし | 文字起こしが「入」で保存先があるときだけ始められる（端末の音は、文字にするために取り込むので）。方式・区間の切り方・md の形は 2.5 と同じ |
| 送る役 | PC の音と端末の音で、送る役（2.5）を同じ1本にする（止めてすぐ別の経路で始めても、送りが重ならないように） |
| 画面を消したとき | 種類が mediaProjection の前景サービスで取り込み、CPU と Wi-Fi のロックを持つ（画面を消しても、取り込みと送りを続けるため） |
| 許可 | 録音（RECORD_AUDIO）。Release 版にも加わる。X の uid を調べるため、X のアプリを `<queries>` に書く |
| 止まるとき | 「停止」、通知の「停止」、Android の画面共有を止めたとき（取り込みの許可が終わる）|
| 止めたあとの最後の区間 | 止めたときに送った最後の区間の行も書いてから、文字起こしの作業スレッドを閉じる（送る役の列の最後に「閉じる」を並べる）。実機で、取り込みサービスがすぐ終わり、最後の区間（7 秒・2 行）を書けずに失ったため（2026-10-23） |

#### 確かめ（2026-10-23、Xiaomi の Android 16、X 12.36.1）

Debug 版の確かめ用の画面（`CaptureProbeActivity`）で、X で Space を流しながら 20 秒ずつ取り込んだ。

| 確かめたこと | 結果 |
|---|---|
| X だけに絞って取れるか | **取れた**（uid 10342。20 秒とも −18〜−48 dBFS、無音の秒は無し） |
| 全部のアプリで取れるか | 取れた（同じくらいの大きさ） |
| X の Space の音の種類 | `USAGE_MEDIA`・`CONTENT_TYPE_SPEECH`（X は Media3 の ExoPlayer で鳴らす）。取り込める種類（通話の種類ではない） |
| 中身 | 取り込んだ WAV を利用者が聴き、Space の声だと確かめた |
| 共有の範囲 | Android の画面のキャプチャの確かめで「**1つのアプリ**」を選び X を選んでも、**取れた**（2026-10-23。20 秒とも −20〜−55 dBFS、無音の秒は無し）。「画面全体」でも取れる。共有の対象が X だけになるので、**「1つのアプリ」で X を選ぶのをおすすめ**とする |
| X が裏に回ったとき | 「1つのアプリ」で X を共有したまま、ホーム画面・ほかのアプリに切り替えても、**取り込みは続いた**（2026-10-23）。X は再生中のまま（一時停止しない）。裏に回っていた間は話し手がたまたま黙っていたが、取り込んだ音に環境音が入っていた（Android が取り込みを止めると完全な無音になる）。**話し声そのものが裏でも入ることは、まだ確かめていない** |

### 2.4 テストのための口

| 口 | 本番の実装 | テスト用の実装 |
|---|---|---|
| `IAudioSource` | WASAPI ループバック | サイン波・WAV ファイル |
| `TimeProvider` | `TimeProvider.System` | `FakeTimeProvider`（無音で埋める刻み・書き込みの見切り・24時間の期限） |
| `IAudioEncoderFactory` | Ogg/Opus（または MP3） | （試作では本物を使い、復号して確かめる） |
| 乱数の口 | `RandomNumberGenerator` | 決まった値を返す偽の乱数 |

時計は、当初の案の `IClock` を作らず、.NET の `TimeProvider` 1つにまとめた。単調な時刻（`GetTimestamp`）と壁時計（`GetUtcNow`）の両方を持ち、テスト用の `FakeTimeProvider` も揃っているため。

これで、PC だけで「サイン波 → 圧縮 → HTTP → 復号」の往復をテストできる。

## 3. 検討して採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| C#＋Kotlin で UDP・Opus を自前に組む | 遅延を詰める仕組み（ジッタバッファなど）が要るが、遅延1秒を許すので作り込みすぎ |
| C++ ＋ Oboe ／ Rust 中心 | 低遅延のための構成で、手間に見合わない |
| C# で両側を揃える（.NET for Android） | Android 側の情報が少なく、Media3 の背景再生の恩恵を受けにくい |
| WebRTC ＋ ブラウザで受ける | ブラウザでは画面を消したまま聴き続けるのが難しい |
| USB 経由（`adb reverse`） | Wi-Fi だけでよいため |
| Flutter で UI を共有 | 音声処理はどのみちネイティブで書くので、共有できる部分が少ない |
| 仮想オーディオドライバ | ドライバの署名などで負担が非常に重い |
| Bluetooth A2DP | 通常の Android は A2DP の受け側になれない |

## 4. 試作で確かめること

### 確かめたこと（PC 側の試作）

- WASAPI ループバックで、PC で鳴らした音が取れる（1kHz の音を2秒鳴らし、`/stream` を取り込んで、その間だけページが大きくなることを見た）。
- 鳴っていない間も、無音で埋めてストリームが途切れずに続く。
- 流している間の2本目は 409 で断られ、1本目が切れると音を取るのを止める。

### 確かめたこと（Android 側の試作。エミュレータ Android 17 で、PC は `10.0.2.2` として見えるもの）

- ExoPlayer が、終わりの無い HTTP の Ogg/Opus ストリームを再生できる（MP3 に替える必要は無かった）。音を出さない設定のエミュレータで確かめたので、再生の状態（AudioTrack が 48kHz・ステレオで動いている）までで、耳では聴いていない。
- 画面を消して90秒、再生と PC との接続が続き、前景サービス（mediaPlayback）として動いていた。
- 画面を消したまま PC 側を止めると、1秒・2秒・4秒・8秒と間をあけて繋ぎ直し、PC 側を起動し直すと再生に戻った。
- 停止を押すと、PC との接続が閉じ、PC 側も音を取るのを止め、繋ぎ直さない。

### 確かめたこと（実機。Xiaomi の Android 16、PC は有線・端末は Wi-Fi の同じネットワーク）

- Wi-Fi 越しに繋がり、利用者が耳で聴いて音が出ることを確かめた。遅延は利用者の体感で約1秒（目安どおり）。
- 画面を消し、開発用のコマンドで「充電器を外した」「深い Doze に入った」状態を作って3分間見た。再生と PC との接続は途切れず、繋ぎ直しも起きなかった（利用者も途切れないことを耳で確かめた）。確かめたあと、端末の状態は元に戻した。
- Xiaomi の端末では、adb でアプリを入れるのに「USB 経由でインストール」の許可と、端末での確認が要る。

### 確かめたこと（ペアリング。実機の Android 16 と、エクスプローラから起動した PC 側）

- 1回で正解したとき、ペアリングして鍵を受け取り、その鍵で再生できた。
- PC で「ペアリングを解除」すると、古い鍵の接続を PC が 401 で断り、端末は鍵を捨てて止まった。
- わざと1回外すと、PC は「続けて 1 回」と記録して数字を作り直し、新しい数字で正解するとペアリングでき、再生の音も聞こえた（利用者が確かめた）。
- 続けて2回外したときの24時間の受け付け停止・起動し直しても続くこと・2分の期限は、自動のテスト（偽の時計）で確かめた。実機では試していない。

### 確かめないと決めたこと

- 実機で、本当に充電器を外したまま長い時間（1時間以上）聴き続けられるか。利用者の判断で確かめない（2026-10-20）。確かめたのは、コマンドで作った Doze の中の3分間まで。

### まだ確かめていないこと

- 実機の Wi-Fi の瞬断からの繋ぎ直し（エミュレータで PC 側を止めて確かめたのみ）。
- バッファを縮めたときの遅延と、途切れにくさの釣り合い。
- PC の音量やミュートと、ループバックで取れる音の関係。
- Windows のファイアウォールの許可の画面（初回の待ち受けで出る。許可は利用者が自分で行う）。手順を README に書く。

## 5. まだ決めていないこと
