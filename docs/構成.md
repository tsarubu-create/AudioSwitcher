# 構成（決定事項）

Windows 11 の PC で鳴っている音を、Android 端末で聴くための構成。ここに書いたことが決定事項の正本で、実装はこれに従う。変えるときは先にこの資料を直す。

## 1. 要件（利用者との確認で決まったこと）

| 項目 | 決定 |
|---|---|
| 用途と遅延 | 音楽を聴くだけ。**遅延は1秒程度まで許す** |
| 取る範囲 | **PC 全体の音**（既定の出力機器に出ている音） |
| PC のスピーカー | 転送中に PC 側を無音にする必要はない（どちらでもよい） |
| つなぎ方 | **Wi-Fi だけ**。受け手の Android は **1台** |
| Android アプリ | 入れてよい。**画面を消したまま聴き続けられること** |
| 配布 | **自分用**（ストアには出さない。コード署名もしない） |
| PC アプリの起動 | **手動で起動**（サインイン時の自動起動はしない） |
| 操作する側 | **Android で再生を押すと、PC が自動で送り始める** |
| Android の版 | 手元の端末は Android 16。**最低は Android 8.0（API 26）** |

## 2. 採った構成：HTTP で流し続ける方式（ネットラジオと同じ形）

```
┌──────────── Win11 PC（C# / .NET 10） ───────────┐        ┌────────── Android（Kotlin） ──────────┐
│ WasapiLoopbackCapture（既定の出力機器）         │        │ Compose の画面（接続先・再生/停止）     │
│   ↓ 音が届かない時間を無音で埋める              │        │   ↓                                      │
│ 48kHz ステレオに整える                          │  Wi-Fi │ MediaSessionService（前景サービス）      │
│   ↓                                             │  HTTP  │   └ ExoPlayer（バッファは 0.5〜1秒）     │
│ 圧縮（Ogg/Opus。駄目なら MP3）                  │ ─────→ │      ・通知／ロック画面の操作             │
│   ↓                                             │        │      ・Wi-Fi ロック・オーディオフォーカス│
│ HTTP サーバ（Kestrel）/stream を流し続ける      │        │      ・切れたら自動で再接続               │
│ タスクトレイに常駐（IP:ポート・ペアリングの数字）│        └──────────────────────────────────────────┘
└─────────────────────────────────────────────────┘
```

### 2.1 PC 側

- **形**: C# / .NET 10（長期サポート版）のタスクトレイ常駐アプリ。手動で起動する。当初は .NET 8 としたが、.NET 8 のサポートが 2026年11月10日に終わるため、利用者の了承を得て .NET 10 に変えた。
- **キャプチャ**: NAudio の `WasapiLoopbackCapture` で既定の出力機器の音を取る。既定の出力機器が変わったら取り直す。
- **無音で埋める**: ループバックは、何も鳴っていない間はデータを返さないことがある（どこかのアプリが音の出口を開いたままだと、無音のデータを返し続ける。試作で両方を見た）。そこで 20ms ごとに時計で刻んでバッファから1フレームを取り出し、足りない分を無音で埋めて、ストリームを途切れさせない（`FramePacer`）。時間は `TimeProvider` の単調な時刻（`GetTimestamp`。中身は `Stopwatch` と同じ）で計る。
- **圧縮**: 第一候補は **Ogg/Opus**（Concentus。C# だけで書かれていてネイティブの DLL が要らない）。128kbps、1パケット 20ms。ExoPlayer が終わりの無い Ogg/Opus のストリームを再生できるかを最初の試作で確かめ、駄目なら **MP3**（NAudio.Lame）に替える。
- **Ogg は自前で書く**: 既成の Ogg 書き出しはページが満杯になるまで溜めるため、数秒遅れる。5パケット（100ms）ごとに1ページを書いてすぐ流す。
- **配信**: ASP.NET Core の最小 API（Kestrel）で `GET /stream` を流し続ける。
- **送り始めと止め方**: `/stream` に接続が来たらキャプチャを始め、切れたら止める。PC 側のトレイには、送り始めるボタンを置かない（Android の再生がそのまま送り始めの合図になる）。
- **接続は1本（先勝ち）**: 受け手は1台なので、同時の接続は1本に限る。流している間に2本目の接続が来たら、**後から来た方を断る**（`409 Conflict`）。
- **切れた接続の見切り**: Wi-Fi の瞬断では、PC から見て古い接続が切れたと分からないまま残ることがある。そのままだと先勝ちのせいで、Android が繋ぎ直しても断られ続ける。これを防ぐため、送ったデータが一定の時間はけない（相手が受け取らない）接続は、切れたと見なして閉じる。見切るまでの時間は、試作では **1回の書き込みが5秒で終わらなければ** とした（`AudioStreamService.WriteTimeout`）。実機の瞬断で確かめて見直す。
- **待ち受け**: 同じ Wi-Fi の端末から繋げるよう、すべてのネットワークの口（`0.0.0.0`）の **ポート 48100** で待ち受ける（起動の引数 `--port` で変えられる）。Windows のネットワークの種類が「パブリック」だとファイアウォールに止められやすいので、手順書に「プライベート」にすることを書く。

### 2.2 Android 側

- **形**: Kotlin / Jetpack Compose / Media3（ExoPlayer）。最低 API 26（minSdk）、対象は手元の Android 16（targetSdk 36）。compileSdk は入っている SDK に合わせて 37。
- **画面を消したまま聴く**: Media3 の `MediaSessionService` を前景サービス（`foregroundServiceType="mediaPlayback"`）として動かす。Android 14 以降で要る `FOREGROUND_SERVICE_MEDIA_PLAYBACK` の権限も宣言する。通知とロック画面からの操作・オーディオフォーカス・Wi-Fi ロック（`setWakeMode(C.WAKE_MODE_NETWORK)`）を Media3 に任せる。メディアセッションの通知は、Android 13 以降の通知の許可（`POST_NOTIFICATIONS`）が無くても出せる。
- **暗号化しない HTTP の許可**: Android 9 以降は暗号化しない HTTP を既定で止めるので、`network_security_config` で許す（PC の IP は変わりうるので、名前を絞らずに許す。自分用として受け入れる）。
- **バッファ**: ExoPlayer の既定は数十秒ためるので、`DefaultLoadControl` を縮める。試作では、ためる量を 0.5〜1.5秒、再生を始めるまで 0.3秒、途切れたあと再開するまで 0.5秒とした。実機で途切れ方を見て見直す。
- **接続先**: 「PC の IP:ポート」を手で入れて保存する（自分用なので、mDNS による自動の発見は後回しにする）。初回は続けてペアリング（2.3）に進む。
- **切れたとき**: Wi-Fi の瞬断や PC の再起動で切れたら、間をあけて繋ぎ直す。試作では、**1秒から倍々に延ばし、15秒で頭打ち**にして、利用者が停止を押すまで回数の上限なく続ける（`ReconnectPolicy`）。繋がったら1秒に戻す。
- **ExoPlayer の中の再試行は切る**: ExoPlayer は読み込みが途切れると、HTTP の Range で「続きから」読み直そうとする。PC の配信はライブで続きが無く、新しいストリームが先頭（見出し）から届くので、続きから読むと Ogg の途中に別のストリームが混ざる。そこで再試行を切ってエラーをすぐ表に出し、上の繋ぎ直しで**最初から開き直す**（試作で、再試行を切らないと別の経路で静かに繋ぎ直してしまうことを見た）。

### 2.3 ペアリング（数字を選ぶ方式）と接続の鍵

同じ Wi-Fi にいる他の機器から聴かれないように、**最初の1回だけ**ペアリングし、以後は PC が発行した接続の鍵で繋ぐ。

#### 流れ

```
Android                                   PC（トレイ）
  │ ① 接続先（IP:ポート）を入れて「つなぐ」   │
  │ ──── POST /pair/start ────────────────→ │ ② 2桁の数字（00〜99）を作り、画面に出す
  │ ←─── 候補5つ（正解1つ＋外れ4つ、順不同） ─ │
  │ ③ PC に出ている数字と同じものを選ぶ       │
  │ ──── POST /pair/answer ────────────────→ │ ④ 合っていれば接続の鍵を発行する
  │ ←─── 接続の鍵 ─────────────────────────  │
  │ ⑤ 鍵を端末に保存                          │
  │ ──── GET /stream（鍵つき）─────────────→ │ ⑥ 鍵を確かめて送り始める
```

- 候補の5つは PC が作る。5つは互いに重ならず、正解は必ずちょうど1つ入る。
- 数字と候補は暗号用の乱数（`RandomNumberGenerator`）で作る。乱数は差し替えられる口から受け取り、テストでは決まった値を入れる。
- 接続の鍵は長い乱数（32バイト）とする。2桁の数字は、鍵を渡す相手を確かめるためだけに使う。
- 受け付けない間に `/pair/start` が来たら断り、Android は「PC で受け付けない状態を解いてください」と出す。
- 数字を出してから **2分** のうちに答えが来なければ、その数字を無効にする。Android はペアリングを最初からやり直す。期限切れは**外れた回数に数えない**。

#### 外れたとき

| 状況 | 扱い |
|---|---|
| 1回外れた | その数字を捨てて、新しい数字と新しい候補で作り直す |
| **続けて2回**外れた | **24時間、ペアリングを受け付けない** |
| 正解した | 外れた回数を0に戻す |

- 受け付けない状態は **PC アプリを起動し直しても続く**（期限と外れた回数を PC に保存する）。
- PC のトレイに **「受け付けない状態を解く」** を置き、持ち主が選び間違えたときは手で解ける。
- 受け付けないのはペアリングだけ。ペアリング済みの端末は、その間も鍵で繋いで聴ける。

#### ペアリング済みのとき

- 受け手は1台なので、ペアリング済みの間は**別の端末からの新しいペアリングを受け付けない**。端末を替えるときは、先にトレイで「ペアリングを解除」する。
- **「ペアリングを解除」**（トレイ）: 保存した鍵を消し、古い鍵を無効にする。端末を替えたときや手放したときに使う。

#### 答えを待っている間・鍵が無効になったとき（利用者と決めた）

- ある端末がペアリングを始めて答えを待っている間（最大2分）に、別の端末がペアリングを始めたら、**後から来た方を断る**。PC に出ている数字が途中で入れ替わらないようにする（接続の先勝ちとそろえる）。
- PC で「ペアリングを解除」したあと、古い鍵を持った Android が繋いできたら、Android は**鍵を捨ててペアリングの画面に戻る**（繋ぎ直しはしない）。
- Android で接続先（PC の IP）を変えても、**鍵は残す**（PC の IP が変わっただけのときに、ペアリングし直さずに済むように）。別の PC に向けた場合は、その PC が鍵を認めないので、上の「鍵が無効」の扱いになる。

#### 通信の取り決め

| 要求 | 応答 |
|---|---|
| `POST /pair/start` | 200: `{"pairingId", "candidates": [5つ]}`。409: ペアリング済み（`"reason": "paired"`）か、別の端末が答えを待っている（`"reason": "busy"`）。423: 受け付けない状態（`"lockedUntil"`） |
| `POST /pair/answer`（`{"pairingId", "answer"}`） | 200: `{"key"}`。400: 外れ（`"candidates"` に新しい5つ。PC には新しい数字が出る）。423: 続けて2回外れて、受け付けない状態になった。410: 数字の期限（2分）が切れたか、知らない `pairingId` |
| `GET /stream`（`Authorization: Bearer <鍵>`） | 200: 流す。401: 鍵が無いか、認めない鍵。409: 流している最中 |

- 鍵は **HTTP のヘッダ**（`Authorization`）で渡す。URL に入れると、ログやブラウザの履歴に残りやすいため。
- 鍵は 32 バイトの乱数を Base64URL にした文字列。PC は SHA-256 のハッシュだけを持ち、届いた鍵のハッシュと、時間の差が出ない比べ方（`CryptographicOperations.FixedTimeEquals`）で比べる。
- PC は、数字を出している間、**画面の右下（タスクバーを除いた作業領域の右下）に、白基調の小さなポップアップ**で数字を出す（利用者と決めた）。
  - 出すもの: 2桁の数字、「端末で同じ数字を選んでください」の一言、残り時間（2:00 から 1 秒ごとに減る。外れて数字を作り直したら、また 2:00 から）、閉じるボタン（×）。
  - × で閉じても、ペアリングは続く（次に数字が変わったら、また出す）。
  - 出すときに入力の焦点を奪わず、タスクバーや Alt+Tab にも出さない（作業中の邪魔にならないように）。
  - 答えが合ったとき・期限が切れたときに消し、外れて作り直したときは数字と残り時間を替える。

#### 保存

- PC 側: 鍵そのものではなく**鍵のハッシュ（SHA-256）**と、受け付けない状態（期限・外れた回数）を、ユーザーごとの場所（`%LOCALAPPDATA%\AudioSwitcher\`）に保存する。PC は届いた鍵のハッシュを比べるだけなので、鍵そのものを持つ必要が無い。保存したファイルが読まれても、鍵は分からない。PC アプリを起動し直しても、鍵で繋がる。
- Android 側: 鍵を Android Keystore の AES 鍵（端末の外に出せない）で暗号化して保存する。
- 鍵と2桁の数字は、ログ・コミット・書き出しファイルに入れない。

#### 24時間の計り方

受け付けない状態は PC アプリを起動し直しても続けるので、単調な時計（`Stopwatch`）では計れない（起動し直すと 0 に戻るため）。期限は **UTC の時刻**で保存し、差し替えられる時刻の口（.NET の `TimeProvider`）から読む。全体ルールの「経過時間は壁時計の差で計らない」の例外で、理由は CLAUDE.md に書く。PC の時計を進めると早く解けるが、PC を触れる人は持ち主なので受け入れる。

#### 守りの強さ（既知の制約）

- 当てずっぽうでも1回で 1/5 の確率で当たる。続けて2回外れたら24時間止めるので、止まるまでに当てられる確率は約 36%（1 − 0.8 × 0.8）。何度も試すことはできない。
- 通信は暗号化しない HTTP なので、同じ Wi-Fi で通信を盗み見できる人には鍵が見える。自分用・家庭用として許す。気になる場合は、あとで HTTPS（自己署名の証明書を Android に覚えさせる形）にする。

### 2.4 テストのための口

| 口 | 本番の実装 | テスト用の実装 |
|---|---|---|
| `IAudioSource` | WASAPI ループバック | サイン波・WAV ファイル |
| `TimeProvider` | `TimeProvider.System` | `FakeTimeProvider`（無音で埋める刻み・書き込みの見切り・24時間の期限） |
| `IAudioEncoderFactory` | Ogg/Opus（または MP3） | （試作では本物を使い、復号して確かめる） |
| 乱数の口 | `RandomNumberGenerator` | 決まった値を返す偽の乱数 |

時計は、当初の案の `IClock` を作らず、.NET の `TimeProvider` 1つにまとめた。単調な時刻（`GetTimestamp`）と壁時計（`GetUtcNow`）の両方を持ち、テスト用の `FakeTimeProvider` も揃っているため。

これで、PC だけで「サイン波 → 圧縮 → HTTP → 復号」の往復をテストできる。

## 3. 検討して採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| C#＋Kotlin で UDP・Opus を自前に組む | 遅延を詰める仕組み（ジッタバッファなど）が要るが、遅延1秒を許すので作り込みすぎ |
| C++ ＋ Oboe ／ Rust 中心 | 低遅延のための構成で、手間に見合わない |
| C# で両側を揃える（.NET for Android） | Android 側の情報が少なく、Media3 の背景再生の恩恵を受けにくい |
| WebRTC ＋ ブラウザで受ける | ブラウザでは画面を消したまま聴き続けるのが難しい |
| USB 経由（`adb reverse`） | Wi-Fi だけでよいため |
| Flutter で UI を共有 | 音声処理はどのみちネイティブで書くので、共有できる部分が少ない |
| 仮想オーディオドライバ | ドライバの署名などで負担が非常に重い |
| Bluetooth A2DP | 通常の Android は A2DP の受け側になれない |

## 4. 試作で確かめること

### 確かめたこと（PC 側の試作）

- WASAPI ループバックで、PC で鳴らした音が取れる（1kHz の音を2秒鳴らし、`/stream` を取り込んで、その間だけページが大きくなることを見た）。
- 鳴っていない間も、無音で埋めてストリームが途切れずに続く。
- 流している間の2本目は 409 で断られ、1本目が切れると音を取るのを止める。

### 確かめたこと（Android 側の試作。エミュレータ Android 17 で、PC は `10.0.2.2` として見えるもの）

- ExoPlayer が、終わりの無い HTTP の Ogg/Opus ストリームを再生できる（MP3 に替える必要は無かった）。音を出さない設定のエミュレータで確かめたので、再生の状態（AudioTrack が 48kHz・ステレオで動いている）までで、耳では聴いていない。
- 画面を消して90秒、再生と PC との接続が続き、前景サービス（mediaPlayback）として動いていた。
- 画面を消したまま PC 側を止めると、1秒・2秒・4秒・8秒と間をあけて繋ぎ直し、PC 側を起動し直すと再生に戻った。
- 停止を押すと、PC との接続が閉じ、PC 側も音を取るのを止め、繋ぎ直さない。

### 確かめたこと（実機。Xiaomi の Android 16、PC は有線・端末は Wi-Fi の同じネットワーク）

- Wi-Fi 越しに繋がり、利用者が耳で聴いて音が出ることを確かめた。遅延は利用者の体感で約1秒（目安どおり）。
- 画面を消し、開発用のコマンドで「充電器を外した」「深い Doze に入った」状態を作って3分間見た。再生と PC との接続は途切れず、繋ぎ直しも起きなかった（利用者も途切れないことを耳で確かめた）。確かめたあと、端末の状態は元に戻した。
- Xiaomi の端末では、adb でアプリを入れるのに「USB 経由でインストール」の許可と、端末での確認が要る。

### 確かめたこと（ペアリング。実機の Android 16 と、エクスプローラから起動した PC 側）

- 1回で正解したとき、ペアリングして鍵を受け取り、その鍵で再生できた。
- PC で「ペアリングを解除」すると、古い鍵の接続を PC が 401 で断り、端末は鍵を捨てて止まった。
- わざと1回外すと、PC は「続けて 1 回」と記録して数字を作り直し、新しい数字で正解するとペアリングでき、再生の音も聞こえた（利用者が確かめた）。
- 続けて2回外したときの24時間の受け付け停止・起動し直しても続くこと・2分の期限は、自動のテスト（偽の時計）で確かめた。実機では試していない。

### 確かめないと決めたこと

- 実機で、本当に充電器を外したまま長い時間（1時間以上）聴き続けられるか。利用者の判断で確かめない（2026-10-20）。確かめたのは、コマンドで作った Doze の中の3分間まで。

### まだ確かめていないこと

- 実機の Wi-Fi の瞬断からの繋ぎ直し（エミュレータで PC 側を止めて確かめたのみ）。
- バッファを縮めたときの遅延と、途切れにくさの釣り合い。
- PC の音量やミュートと、ループバックで取れる音の関係。
- Windows のファイアウォールの許可の画面（初回の待ち受けで出る。許可は利用者が自分で行う）。手順を README に書く。
